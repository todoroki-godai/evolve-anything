## 1. 決定

**ユーザー決定（2026-08-18）**: 「9/9 まで待ちたくない。1週分から出す」。

指摘率の表示条件を **「全量判定の確定週が4週連続」から「確定週が1件でもあれば、その週の率を
点として出す」へ変更する**。系列（推移）表示のゲートは `GATE_CONSECUTIVE_WEEKS=4` のまま維持する。

**これは解釈でなく方針変更である**（round1 [Must]）。ADR-054 §2.9 は

> 全量判定（カバレッジ100%）の確定週が k=4 週連続で揃うまで、指摘率の系列を表示しない。
> **揃わない間は `指摘率: 未測定（判定カバレッジ X/Y）` のみ。**

と明記しており、CLAUDE.md 体験3 も表示条件を「全量判定した週が4週連続」としている。
よって**本設計は ADR-054 §2.9 と CLAUDE.md 体験3 の記述を改訂する**（§2-5）。

`GATE_CONSECUTIVE_WEEKS` の値自体に統計的導出は文書化されていない（「運用が安定しなければ
数字は出ない」という運用信頼の歯止めとして選ばれた値）。本設計は k を変更しない。

## 2. 変更

判定・集計・freeze の契約は一切変えない。**表示層と、それに必要な gate 情報の追加のみ**。

1. `compute_display_gate`（`correction_rate.py:538-564`）の結果に、**系列可否とは独立の
   追加フィールド**を載せる。**既存の `gate_open` の判定式（`best_run >= k`）は一切変更しない**
   （round2 [Must]）:
   - (a) `point_week` — 点表示に使う週。**`weeks` 中で最大 `week_id` を持つ `measured=True` の週**
   - (b) `current_run_length` — **現在の**連続 run 長。**点表示の進捗表示専用**で、
     状態分岐には使わない
   - (c) 入力 `weeks` の順序契約: 現行 `compute_display_gate` は昇順を前提にするだけで
     内部ソートしない。**追加フィールドの算出は `week_id` で明示的にソートしてから行う**
     （非ソート入力でも正しい値になることをテストで固定する）
2. `results_board` の指摘率セクションを3状態にする。**実装は既存の閉ゲート分岐・開ゲート分岐を
   一字も変えず、`_render_exclusion_diagnostics` の後、両者の間に点分岐を挿入する**:

   | 状態 | 条件 | 出力 |
   |------|------|------|
   | (iii) 系列 | **既存の `gate_open` が真**（＝ `best_run >= k`。変更前と同じ判定） | **変更前と完全に同一**の系列表示 |
   | (ii) 点 | `gate_open` が偽 **かつ** `point_week` が存在する | 下記の必須要素をすべて含む点表示 |
   | (i) 未測定 | `gate_open` が偽 **かつ** `point_week` が無い | **変更前と完全に同一**の `指摘率: 未測定（判定カバレッジ X/Y・<week_id>）` |

3. 状態 (ii) の**必須要素**（1つでも欠けたら出さない）:
   - (a) 対象週の `week_id`
   - (b) 分子/分母の実数
   - (c) 「1週分。推移は k 週連続で表示」の但し書き
   - (d) 連続 run の進捗 `n/k`（n は連続 run 長）
   - (e) **最新候補週のカバレッジと未測定理由**（古い確定週だけを見せて現在の欠測を隠さない）
   - (f) **PJ 別内訳**（`MIN_PJ_RATE_DENOM=10` の floor 込み。全体率だけで構成比変化を
     改善と誤読させない）
4. `GATE_CONSECUTIVE_WEEKS` は **4 のまま変更しない**
5. **ADR-054 §2.9 と CLAUDE.md 体験3 の記述を改訂する**（方針変更の記録。CLAUDE.md には
   数値・到達状況を書かない既存方針に従い、表示条件の**規則**だけを書き換える）

## 2.1 変更しない

- `FREEZE_DELAY_DAYS`・freeze 済み週の不変契約（確定後に値が動かない）
- 母集団フィルタ・分子分母の定義・`judged_at` 必須の判定
- `MIN_PJ_RATE_DENOM=10`（点表示でも同じ floor を適用する）
- judge の日次上限（別論点。上げるなら `llm-batch-guard` に従いユーザー確認）

## 3. 不変条件

**「バイト等値」の範囲**（round1 [Nit]）: 指摘率**ブロック全体**（見出し行・率の行・
除外 diagnostics 行・PJ 別内訳を含む、次の見出しまで）を対象とする。

- **I1（後退なし）**: 状態 (i) のとき、指摘率ブロックが変更前と**バイト等値**
- **I2（点は必ず素性つき）**: 状態 (ii) のとき、§2-3 の (a)〜(f) が**すべて**含まれる。
  期待文字列との**完全一致**で固定する（包含検査は禁止）
- **I3（系列を騙らない）**: 状態 (ii) のとき、複数週の並び・推移を示す表現が**現れない**
  （複数の week_id が出ない・矢印/推移語が出ない）
- **I4（100% 未満の週の率は絶対に出ない）**: `measured=False` の週は点表示の候補に**入らない**。
  候補が空なら状態 (i) に落ちる
- **I5（k 到達時の非破壊）**: 状態 (iii) のとき、指摘率ブロックが変更前と**バイト等値**
- **I6（欠測を隠さない）**: 状態 (ii) で、点の対象週より**新しい**確定候補週が未測定なら、
  その週の `week_id`・カバレッジ・未測定理由が出力に含まれる
- **I7（Simpson 対策）**: 状態 (ii) で PJ 別内訳が出力に含まれる。かつ
  (a) **その週に judged が 1 件以上ある PJ を全件列挙**する（一部を落とさない）
  (b) **PJ 別 `judged` の合計＝全体の分母、PJ 別 `tp` の合計＝全体の分子**
  (c) 分母 < `MIN_PJ_RATE_DENOM` の PJ は率を出さず件数のみ出す
  (d) **内訳が空なら点表示そのものを行わない**（状態 (i) に落ちる）
- **I8（進捗の定義）**: 出力の `n/k` の `n` は**現在の連続 run 長**であり、
  **常に `n <= k`**。非連続な確定週が k 件以上あっても `n` は run 長を超えない。
  `n` は**表示専用**で状態分岐には使わない
- **I9（点は最新の確定週）**: 点の対象週は `weeks` 中で **`week_id` が最大の `measured=True` の週**。
  入力 `weeks` が非ソートで来ても同じ週が選ばれる

## 5. 未実測の前提

- **1週分の点値が利用者の判断に役立つかは未測定**。本設計はこれを主張せず、ユーザー決定に従う
- **W33 が cutoff（08-20）時点でも 100% を維持するかは未確定**（M3）。08-18 のスナップショットで
  100%。維持できなければ初表示は次の確定週まで延びる
- **実効処理量は未測定**（M5）。日次上限は 200 だが 8/18 は 170 件・1バッチ失敗。
  バッチ失敗率・token limit・newest-first の影響を織り込んだ実効値は測っていないため、
  「上限200 − 流入147 = 余力53」という単純差は**根拠として使わない**
- **点表示時の典型的な分母**（全体・PJ 別）は M2 の 629 以外に実測がない。floor で率が隠れる
  PJ が何件になるかは未測定
- **非ソート入力で `current_run_length` / `point_week` が正しく出るかは未測定**。現行
  `compute_display_gate`（`correction_rate.py:541`）は昇順を呼出契約として仮定するだけで
  内部ソートしない。§2-1-(c) のとおり**明示ソートを契約として決め、テストで固定する**
- **k=4 が系列表示の閾値として妥当かは未検証**（導出根拠が文書化されていない）。本変更は
  k を触らないため、この未検証は解消も悪化もしない
