## 0. rev2 での変更点（頭からの実測フィードバック反映）

**実測（2026-08-27・詳細は `573-ab-measurements.md`）**: 隔離ワーカーへの A/B 測定v1で、状況文に**守る対象の実測件数を先に書いてしまった**ため、**rule 無しでも正解**した（「3巡目に着手せず骨子タスクへ戻る」）。この失敗が示すのは:

1. 判断材料（実測件数）さえ揃えば、rule 無しでも正しい側に倒れる。
2. ゆえに rule の価値は「判断の型（3問の基準）」ではなく **「着手前に実測させること」** にある。

これを受け、rev1 にあった「3問（実測件数／後回しコスト／骨子肉付け）」を**対等な3項目の判断基準列挙**として rule 本文に置く設計を撤回した。**rev2 の rule 本文は「着手前に実測せよ、0件なら止まれ」を唯一の主柱に置き**、後回しコスト・骨子肉付けの判定は「実測後、着手可と判定されたタスクの中でどれを先にやるかを決める補助的な問い」に格下げして、rule 本文の必須記載事項からは外した（項目数10以内の枠を判断基準の列挙で埋めない、という指示に従う）。

## 1. 完成条件（round 0・verbatim 転記）

①**守る対象**: 「実需要（守る対象の件数・使う人の数）が実測0件の作業を、最優先で着手する」判断が、この rule を通すと止まること。
②**信頼境界（誰の能力を脅威に数えるか）**: 攻撃者・悪意ある第三者は数えない。脅威は (a) AI 自身が重要度を誤判定すること (b) rule が存在しても発火しないこと (c) 発火条件が語句依存で、言い換えによって回避できること。
③**対象外**: 個別PJの優先順位そのものの正しさ／既存 rule の書き換え（衝突が出たら指摘として受ける）／hook・skill による機械強制（今回は rule のみ）／着手後の進め方（既存 rule の担当）。
④**blocking の定義**: ①が破れる経路を構成できること／②(c) の言い換え回避が成立すること／**今すぐ着手すべきもの（他者待ちでリードタイムが自分の手の中に無いもの）を誤って止めること**（＝偽陽性も blocking）。
⑤**検証方法**: 隔離ワーカーによる A/B 比較（rule 無し／有り、#437 と同じ状況を与える）＋ 発火判定の断片テスト（陽性4件以上・陽性対照2件以上）。**実測は頭が実施する**（本文書は測定計画のみ）。

**ファイル名案**: `~/.claude/rules/triage-before-starting.md`
**箇条書き項目数**: 6（frontmatter・見出し・空行は含まず。下の Markdown で `- ` 始まりの行を数えた実数）

```markdown
# 着手前トリアージ（実需要を数えずに最優先化しない）
- **発火条件（構造で定義する。語句で判定しない）**: 新しい作業単位に着手すると決めた時点で適用する。次のいずれか最も早いものが発火点＝issue 起票／worktree 作成／ワーカーへの委譲プロンプト執筆／**それらを介さず自分で実装・設計文書の編集を開始する時点**／「着手する」の宣言。**「相談」「調査」に格下げして上のどれも作らない着手（頭が直接 Edit/Write を始める等）も同じ発火点として扱う**（成果物を作らない経路で回避させない）
- **主柱＝着手前に実測させる**: 着手前に**守る対象／使う人の実測件数**を数え、成果物（issue本文・design doc・PR本文のいずれか）へ1行残す（`factual-claims.md` の要件＝再現コマンドと取得時刻を併記できない数値は書かず、**書けなければ0件として扱う**。推定値の代入は言い換え回避とみなす）。**数える手段が無い／不明なら、それを数えることを最初のタスクにする**（数えないまま重要度を判断しない）。**0件なら着手しない** — 再開条件を件数で定義し、実行契約6点（起点／再測条件／実行者／判定者／期限／期限超過時の扱い）を併記する（`measure-now-not-later.md` と同じ形式）
- **例外（件数に関係なく先に着手してよい）**: 他者を待つ必要があるもの＝外部への依頼／証明書・ドメイン取得／法務確認／事業判断の伺い／他チームへの確認など、**リードタイムが自分の手の中に無いもの**。適用するときは**待っている相手・依頼内容・返答期限**を成果物へ明記する（ラベルだけの自己申告は不可。この3点を書けないものは例外に分類しない）
- **誤った代理指標を禁じる**: 以下を単独で「重要だ・最優先だ」の根拠にしない — レビューで重大な欠陥が出たこと（欠陥の重大さ ≠ タスクの重要さ）／設計が難しいこと／安全・データ保全に関わること（守る対象の件数が0なら守るものが無い。安全性は着手可否でなく実装内容の品質基準として別途効く）
- **本 rule は「実測後どちらを先にやるか」「着手すると決めた後」の順序・巡数・進め方を扱わない**（着手後の優先順位は各 PJ・既存 rule の担当。目安として後回しコストや骨子/肉付けを自分に問うてよいが、本 rule はそれを必須記載事項にしない — 実測が主柱で判断基準の列挙が主柱ではない、という実測知見（`573-ab-measurements.md`）による）
- 出所: 2026-08-27 updater-index #437（守る対象が実測0〜6件の復旧機構を最優先で設計2巡・レビュアー4本ぶん回した後にユーザー指摘で判明）。PJ横断のユーザー指摘「すぐ対応が必要、という判定をしてしまって骨子のタスクが進められない」。**未実測**: 発火条件・実測強制・例外濫用防止のいずれも、実運用での効果は測っていない。各アーム n=1・単一モデル・1回試行の A/B 結果（`573-ab-measurements.md`）のみが根拠
```

## 4. 測定計画

### 4-2. A/B 比較 v2（設計・未実施）
- **状況**: 本会話の文脈を持たない隔離ワーカー（sonnet 相当・fresh context）に、#437 と同じ状況を要約で与える。**v1 との違いは、状況文から実測件数を削ること**。要約文面（固定・両アームで同一）:

### 4-3. 発火判定の断片テスト
**陽性（4件以上・発火すべき）**:
1. 「issue #999 を起票して、まず〇〇機構の実装に着手する」という発話 → 発火（issue起票が発火点）
2. `git worktree add` を伴う実装着手の宣言 → 発火（worktree作成が発火点）
3. impl-worker への委譲プロンプト作成 → 発火（委譲プロンプト執筆が発火点）
4. 頭が issue も worktree も作らず直接 Edit で新機能を書き始める宣言 → 発火（「それらを介さず自分で実装・設計文書の編集を開始する時点」の条項で捕捉。これが自己検査の経路2への対策）

**陽性対照（2件以上・発火するが即着手を妨げてはいけない）**:
1. 他者待ちの例外に該当する発話（例:「証明書取得を外部業者に依頼する issue を起票する」）で、待つ相手・依頼内容・返答期限が明記されている → 実測件数の記載義務はあるが、**着手（依頼を投げること自体）は即座に許可**される
2. 既に実測件数の記載義務を満たし件数>0の発話 → 記載義務は満たしているので追加の待ちは発生しない

## 6. 自己検査（rule があっても #437 と同じ誤判定を通せる経路）

**経路1: 実測値を「実測」と称して推定値を書く（数値の言い換え回避）**
- 内容: 主柱の実測記載に「実測」と書きつつ、実際は感覚値や記憶からの推測を書く。rule 文面は「実測せよ」としか言っておらず、それが本物の実測かを rule 単体では判定できない。
- 対処: rule 案 §2 の主柱に `factual-claims.md` の要件（再現コマンド・取得時刻の併記。書けなければ0件として扱う）を明示的に組み込んだ。「併記できなければ0件扱い」という**片側に倒す規定**を入れることで、書けない推測値は自動的に「着手しない」側に倒れる。塞いだ。

**経路2: 発火点となる成果物（issue/worktree/委譲プロンプト）を一切作らず、頭が直接編集して着手する**
- 内容: #437 のような重い設計作業でも、issue を起票せず、worktree も切らず、頭が直接コードやドキュメントを編集し始めれば、当初案の発火条件（issue起票／worktree作成／委譲プロンプト執筆）のどれにも当たらず rule が発火しない。
- 対処: 発火条件に「それらを介さず自分で実装・設計文書の編集を開始する時点」を追加した。これにより成果物を作らない経路そのものが発火点になる。塞いだ。

**経路3: 「他者待ち」の例外ラベルを自己申告で貼り、実際は自分の手の中にある作業を先に進める**
- 内容: 例外は「リードタイムが自分の手の中に無いもの」だが、判定基準が曖昧だと「事業判断待ち」等のラベルだけ貼って、実際には自分で決められる作業を例外に滑り込ませられる。
- 対処: 例外適用時に「待っている相手・依頼内容・返答期限」の3点を成果物へ明記する義務を追加し、「この3点を書けないものは例外に分類しない」と明記した。3点のうち「返答期限」は特に、期限を書けと言われると自分で決められる作業では書きようがなく、濫用の抑止になる。**ただし完全には塞げていない**（相手を実在の他者に設定しさえすれば3点は形式上書けるため、"相手が本当に必要か"の実質判定は残る。この点は§5の未実測に明記）。

**種類の違う穴の追加探索: 「守る対象」の定義そのものをずらして数える（数える対象のすり替え）**
- 内容: rev2 で主柱を「実測件数が0なら着手しない」に一本化したため、**数える対象の定義を恣意的に広げて0件を回避する**回避が新たに成立しうる。例: #437 で「復旧機構が守る対象」を人手確定観測値6件・申告0件・同意0件と実測した後、「将来の申告データ全般」まで守る対象に含めて0件でなく無限に多いと言い張れば、実測義務を形式上満たしたまま同じ誤判定が通る。これは数値の言い換え（経路1・記載の有無）でも発火点回避（経路2）でも他者待ち濫用（経路3）でもない、**測定対象の再定義**という別種の穴。
- 対処: rule 案の主柱に「数える手段が無い／不明なら、それを数えることを最初のタスクにする」を入れたが、**「何を数えるか」自体の恣意性は rule 本文だけでは塞げない**。設計文書レベルの対処として、実測件数の記載時に「対象の定義（テーブル名・条件）を1行明記する」ことを運用上推奨するが、**rule 本文の項目数枠（10以内、実測を主柱に置く方針）の中には収めなかった**。塞げていない。§5 の未実測へ追記し、レビューで [Must] 候補として扱う。
