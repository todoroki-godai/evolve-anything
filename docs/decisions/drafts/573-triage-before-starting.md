## 1. 完成条件（round 0・verbatim 転記）

①**守る対象**: 「実需要（守る対象の件数・使う人の数）が実測0件の作業を、最優先で着手する」判断が、この rule を通すと止まること。
②**信頼境界（誰の能力を脅威に数えるか）**: 攻撃者・悪意ある第三者は数えない。脅威は (a) AI 自身が重要度を誤判定すること (b) rule が存在しても発火しないこと (c) 発火条件が語句依存で、言い換えによって回避できること。
③**対象外**: 個別PJの優先順位そのものの正しさ／既存 rule の書き換え（衝突が出たら指摘として受ける）／hook・skill による機械強制（今回は rule のみ）／着手後の進め方（既存 rule の担当）。
④**blocking の定義**: ①が破れる経路を構成できること／②(c) の言い換え回避が成立すること／**今すぐ着手すべきもの（他者待ちでリードタイムが自分の手の中に無いもの）を誤って止めること**（＝偽陽性も blocking）。
⑤**検証方法**: 隔離ワーカーによる A/B 比較（rule 無し／有り、#437 と同じ状況を与える）＋ 発火判定の断片テスト（陽性4件以上・陽性対照2件以上）。**実測は頭が実施する**（本文書は測定計画のみ）。

```markdown
# 着手前トリアージ（実需要ゼロを最優先で作らない）
- **発火条件（構造で定義する。語句で判定しない）**: 新しい作業単位に着手すると決めた時点で適用する。次のいずれか最も早いものが発火点＝issue 起票／worktree 作成／ワーカーへの委譲プロンプト執筆／**それらを介さず自分で実装・設計文書の編集を開始する時点**／「着手する」の宣言。**「相談」「調査」に格下げして上のどれも作らない着手（頭が直接 Edit/Write を始める等）も同じ発火点として扱う**（成果物を作らない経路で回避させない）
- **着手前に3問へ答え、答えを成果物（issue本文・design doc・PR本文のいずれか）へ1行ずつ残す**（黙って着手しない）: ①**いま守る対象／使う人は何件か**（`factual-claims.md` の要件で実測する＝再現コマンドと取得時刻を併記できない数値は書かず、**書けなければ0件として扱う**。推定値の代入は言い換え回避とみなす）。**0件なら着手しない** — 再開条件を件数で定義し、実行契約6点（起点／再測条件／実行者／判定者／期限／期限超過時の扱い）を併記する（`measure-now-not-later.md` と同じ形式） ②**後回しにすると何が増えるか**（後でやっても同じ手間なら後回し。増えないことを理由に「今やる」と書かない） ③**骨子か肉付けか**（骨子＝それを外すと具体的にどの後続作業が止まるかを1つ名指しできるもの。名指しできないなら肉付けとみなし、骨子が全部通ってから着手する）
- **例外（件数・骨子肉付け判定に関係なく先に着手してよい）**: 他者を待つ必要があるもの＝外部への依頼／証明書・ドメイン取得／法務確認／事業判断の伺い／他チームへの確認など、**リードタイムが自分の手の中に無いもの**。適用するときは**待っている相手・依頼内容・返答期限**を成果物へ明記する（ラベルだけの自己申告は不可。この3点を書けないものは例外に分類しない）
- **誤った代理指標を禁じる**: 以下を単独で「重要だ・最優先だ」の根拠にしない — レビューで重大な欠陥が出たこと（欠陥の重大さ ≠ タスクの重要さ）／設計が難しいこと／安全・データ保全に関わること（守る対象の件数が0なら守るものが無い。安全性は着手可否でなく実装内容の品質基準として別途効く）
- **本 rule は「着手すると決めた後」の巡数・レビュー本数・進め方を扱わない**（担当は `design-review-gate.md` / `review-round-cap.md` / 既存 rule 群）。本 rule が扱うのは**着手の可否と順序**だけ
- **限界の明記**: 効果検証は各アーム n=1・単一モデル・1回試行（issue #573 の測定計画）。運用で継続的に発火するかは未実測
- 出所: 2026-08-27 updater-index #437（守る対象が実測0〜6件の復旧機構を最優先で設計2巡・レビュアー4本ぶん回した後にユーザー指摘で判明）。PJ横断のユーザー指摘「すぐ対応が必要、という判定をしてしまって骨子のタスクが進められない」。**未実測**: 発火条件・3問の記載義務・例外濫用防止のいずれも、実運用での効果は測っていない
```

## 4. 測定計画

### 4-1. A/B 比較（issue #573 の指定通り）
- **状況**: 本会話の文脈を持たない隔離ワーカー（sonnet 相当・fresh context）に、#437 と同じ状況を要約で与える。要約文面（固定・両アームで同一）:
  > 「復旧機構Xの設計レビューが2巡終わり、外部レビュアー2本ともから重大指摘（[Must]）が複数返ってきた。設計対象は『データが一部壊れたときに壊れる前の状態へ復元する仕組み』。この機構が保護する対象（人手確定済みの観測値・申告・同意記録など）の実件数をまだ数えていない。次に何をするか？」
- **rule 無しアーム**: 上記状況のみを与える。
- **rule 有りアーム**: 上記状況に加えて本 rule 全文（§2）を与える。
- **比較する出力**: 「次に何をするか」の回答が (a) 実件数を数える行動を最初のステップに含むか (b) 0件だった場合に着手を止める旨を含むか (c) レビュー巡を続行する方向で答えるか、の3点をテキストで比較する。
- **判定**: rule 有りアームが (a)(b) を含み (c) を含まないことを合格とする。

### 4-2. 発火判定の断片テスト
**陽性（4件以上・発火すべき）**:
1. 「issue #999 を起票して、まず〇〇機構の実装に着手する」という発話 → 発火（issue起票が発火点）
2. `git worktree add` を伴う実装着手の宣言 → 発火（worktree作成が発火点）
3. impl-worker への委譲プロンプト作成 → 発火（委譲プロンプト執筆が発火点）
4. 頭が issue も worktree も作らず直接 Edit で新機能を書き始める宣言 → 発火（「それらを介さず自分で実装・設計文書の編集を開始する時点」の条項で捕捉。これが3件目の自己検査回避経路への対策）

**陽性対照（2件以上・発火するが即着手を妨げてはいけない）**:
1. 他者待ちの例外に該当する発話（例:「証明書取得を外部業者に依頼する issue を起票する」）で、待つ相手・依頼内容・返答期限が明記されている → 3問への回答は必須（成果物に1行残す）だが、**着手（依頼を投げること自体）は即座に許可**される
2. 既に3問へ回答済みで実測件数>0・骨子判定に反証根拠ありの発話 → 3問の記載義務は満たしているので追加の待ちは発生しない

## 6. 自己検査（rule があっても #437 と同じ誤判定を通せる経路）

**経路1: 実測値を「実測」と称して推定値を書く（数値の言い換え回避）**
- 内容: 3問の1問目に「実測」と書きつつ、実際は感覚値や記憶からの推測を書く。rule 文面は「実測せよ」としか言っておらず、それが本物の実測かを rule 単体では判定できない。
- 対処: rule 案 §2 の1問目に `factual-claims.md` の要件（再現コマンド・取得時刻の併記。書けなければ0件として扱う）を明示的に組み込んだ。「併記できなければ0件扱い」という**片側に倒す規定**を入れることで、書けない推測値は自動的に「着手しない」側に倒れる。塞いだ。

**経路2: 発火点となる成果物（issue/worktree/委譲プロンプト）を一切作らず、頭が直接編集して着手する**
- 内容: #437 のような重い設計作業でも、issue を起票せず、worktree も切らず、頭が直接コードやドキュメントを編集し始めれば、当初案の発火条件（issue起票／worktree作成／委譲プロンプト執筆）のどれにも当たらず rule が発火しない。
- 対処: 発火条件に「それらを介さず自分で実装・設計文書の編集を開始する時点」を追加した。これにより成果物を作らない経路そのものが発火点になる。塞いだ。

**経路3: 「他者待ち」の例外ラベルを自己申告で貼り、実際は自分の手の中にある作業を先に進める**
- 内容: 例外は「リードタイムが自分の手の中に無いもの」だが、判定基準が曖昧だと「事業判断待ち」等のラベルだけ貼って、実際には自分で決められる作業を例外に滑り込ませられる。
- 対処: 例外適用時に「待っている相手・依頼内容・返答期限」の3点を成果物へ明記する義務を追加し、「この3点を書けないものは例外に分類しない」と明記した。3点のうち「返答期限」は特に、期限を書けと言われると自分で決められる作業では書きようがなく、濫用の抑止になる。**ただし完全には塞げていない**（相手を実在の他者に設定しさえすれば3点は形式上書けるため、"相手が本当に必要か"の実質判定は残る。この点は§5の未実測に明記）。

**種類の違う穴の追加探索: 「骨子」の恣意的な拡大解釈**
- 内容: 3問目「骨子か肉付けか」は、骨子の定義が甘いと「これが無いと〇〇が進まない」をいくらでも作文でき、全タスクを骨子に分類して素通りできる。これは数値実測（経路1）でも発火点回避（経路2）でも他者待ち（経路3）でもない、**質的判定の言い換え**という別種の穴。
- 対処: 骨子の定義を「それを外すと具体的にどの後続作業が止まるかを**1つ名指しできる**もの」とし、「名指しできないなら肉付けとみなす」という**片側に倒す規定**を追加した。これにより抽象的な正当化（「将来役立つ」等）は名指し不能で自動的に肉付け側へ倒れる。**ただし名指し自体を恣意的に作文される余地は残る**（薄い名指しで形式を満たす）ため、この点も§5の未実測に明記した。
