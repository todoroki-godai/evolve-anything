## 2. 定義（1行）

> **柱1の成功指標 = 捕捉率（capture recall）: 「ユーザーが実際に修正した発話」のうち、
> 決定論の記録側が自動で捕まえた割合。高いほど良い。**

**方向を1つに固定する**（rev.1 の自己矛盾を是正）。本文書・実装・表示のすべてで
**捕捉率（高いほど良い）を主指標**とし、「取りこぼし率」は `1 − 捕捉率` の派生表示としてのみ使う。
数値の横には必ず `捕捉率 X%（取りこぼし Y%）` の両方を出し、読み違いを構造で防ぐ。

### 2.1 二層構成（主＝オフライン / 従＝オンライン）

| 層 | 何を測るか | 分母 | 分子 | 状態 |
|---|---|---|---|---|
| **L1（主）オフライン捕捉率** | 固定ラベル済みコーパスに対する本番検出関数の recall | `a0_eval_set.jsonl` の `label == "TP"` 件数 | そのうち本番 `detect_correction` が hit した件数 | **今日から算出可**（P9）。LLM 非依存・判定スループットに依存しない |
| **L2（従）オンライン週次捕捉率** | 実運用の週次で judge が拾った修正のうち hook も拾えた割合 | その週に judge が「修正」と判定した発話 | そのうち hook も同一発話を検出した件数 | **保留**（P11 の突合キー破損を直すまで算出不能） |

**L1 を主に据える理由**: 柱3の指摘率は判定スループット（未判定 6,353件・処理200件/日）に律速され、
確定週が出るまで無表示になる。**L1 は同じボトルネックを共有しない**ため、柱1の完成を柱3の完成に
人質に取られない。ADR-054 §3.3 の G1 が llm_judge レーンで既にこの方式を通している（P8）ので、
方法論の新規性もゼロ＝新 store も新 channel も作らない（#379 Step1 遵守）。

### 2.2 L2 の突合キー（P11 の是正・実装時の契約）

L2 を再開するときの突合キーは **`session_id` + 発話本文の完全一致** とする。
`timestamp` は使わない（P11: hook は発話時刻でなく hook 実行時刻を書くため、実測で約70ms のズレ
＋書式差が生じ、完全一致 join が構造的に 0 件になる）。本文一致で衝突する場合（同一セッション内で
同じ短文を複数回打つ）は、**衝突した組をまとめて1件として扱い、その旨を meta に出す**
（黙って先頭を採らない）。なお `hooks/correction_detect.py:131` を発話時刻に直すのは
**別 issue**（既存レコードの意味が変わるため単独で判断が要る）。

## 3. なぜこの定義か（対案との比較）

| 案 | 内容 | 採否 |
|---|---|---|
| **E. オフライン捕捉率（本案 L1）** | 固定ラベル済みコーパスに対する本番検出関数の recall | **採用（主）**: 決定論・数秒・判定スループット非依存。実装済み（P9）。cold review 提案 |
| A. オンライン週次捕捉率（本案 L2） | judge の TP のうち hook が捕まえた割合 | **採用（従・保留）**: 実運用の実態を映す唯一の層だが P11 で現状算出不能 |
| B. セッション単位 capture_rate(#421) | 活動セッションのうち correction を持つ割合 | 不採用: 分母が30日13件（P4/P5）で母数不足。取りこぼしの中身が見えない |
| C. 手直し回数の減少 | ユーザーが直す回数そのもの | 不採用: 柱3の指摘率(a)として定義済み。二重管理 |
| D. 記録件数の絶対量 | corrections の件数 | 不採用: 分母が無く「少ないのが仕様か漏れか」を判別できない（#421 が既に否定） |
| F. 人間 y/n 確定分のみを真値にする | 朝の確認でユーザーが是と答えた件のみ分母に使う | **将来採用**: judge=真値の割り切り（§6）を外せる唯一の道。ただし現状件数が少なく分母不足。L1 の評価セット拡充と同時に蓄積を始める |

柱1がユーザーに約束しているのは「記録は全自動・無音」。**この約束の破れ方は「静かに取りこぼす」
こと**であり、捕捉率はそれを直接測る唯一の指標である。

## 4. v2.0.0 の発行条件（rev.2・4条件）

「測れるようになったら v2」をそのまま適用すると、**捕捉率 10% をそのまま表示するだけで名乗れて
しまう**（P9）。またパターンを広げれば recall は上がるので、**精度の下限を同時に課さないと
指標をゲームできる**。よって条件を4つに分ける。

1. **測れる**: `bin/evolve-audit --growth` の戦果ボードに L1 捕捉率が Wilson 95% CI つきで出る
2. **母数がある**: 評価セットの `TP` が **30件以上**（P10: 現状10件では CI 幅38pt で 10% と 50% を
   区別できない。30件なら CI 幅は概ね半分になる）。**拡充は本番パターン変更より先に凍結する**
   （後出しでラベルを足すと指標をゲームできる。拡充分の抽出 seed と実施日を記録する）
3. **意味がある（下限）**: 捕捉率の **Wilson 95% CI 下限が 30% を上回る**（点推定でなく CI 下限で
   判定する。点推定だけだと小さい n で偶然に到達しうる）。**この 30% は暫定**で、拡充後の
   実測分布を見て確定する
4. **壊れていない（精度の床）**: 同時に precision の **Wilson 95% CI 下限が 50% を上回る**。
   これが無いと「`。` にマッチさせる」で recall 100% にでき、条件3が無意味になる

**3・4 の下限つきは採用が確定した**（2026-08-18 ユーザー判断「下限あり」）。入れないと v2 は
「壊れた数字を表示できた版」になる。よって **v2 は記録の修理が実効を持つまで名乗れない＝時期は
読めない**、という帰結もあわせて受け入れる。

**ゲーム防止（cold review [Must]6）**: 条件は「最良の週を1つ選ぶ」形にしない。L1 は固定コーパスに
対する単一の値なので週の選択自体が存在せず、この抜け道は構造的に閉じる。L2 を将来 headline に
昇格させる場合は、柱3と同じく「カバレッジ100%確定週のみ・k週連続」ゲートを課し、かつ
**90日で期限切れになった発話を「判定済み」として数えない**こと（`correction_rate.py:219-227` の
now−90日境界により、判定が終わったのでなく期限切れで 100% に見える週が生じうる）。

## 5. 実装の順序（この文書の範囲外・着手は別 issue）

1. 本文書のレビュー通過 → 指標を ADR-054 §3.3 の G1 と並ぶ **G2（柱1捕捉率ゲート）** として正式採録
2. **評価セットの拡充**（TP 30件以上・条件2）。`a0_capture_replay.py dump-sample` を新 seed で回し、
   ラベル付けする。**既存86件は削除・改変しない**（再生成不能な資産）
3. L1 捕捉率の算出を戦果ボードへ1行追加（表示淘汰リストに入れない）。算出は
   `a0_capture_replay.py evaluate` の計算部を共通化して呼ぶ（式を再実装しない）
4. Phase A の記録修理（A0/A1/A2/A3/A5・#478 #480）→ **修理のたびに L1 を再実行して効果を確認する**
   （L1 は数秒なので修理の回帰ゲートとしてそのまま使える）
5. L2 は P11（突合キー）を別 issue で直してから着手。それまで戦果ボードには `not_measured` と明示

**`pattern_version` の層別**（cold review [Should]）: L1 を時系列で比較するときは、検出パターンの
バージョンが混ざると「捕捉率が上がった」のが修理の効果かパターン変更の効果か分からなくなる。
戦果ボードには **算出時点の `pattern_version` を併記**し、版が変わった点を系列上に明示する。

## 6. この設計が依拠する前提のうち、実測で裏取りされていないもの

- **評価セットが母集団を代表しているか**: 層化ランダム抽出・seed 固定で抽出したが（`dump-sample`）、
  抽出窓は 2026-08-12 時点の固定窓であり、その後の発話分布の変化は反映されていない。拡充時に
  窓を延ばすなら、**旧窓分と新窓分を層別して両方報告する**（混ぜて1つの率にしない）
- **judge を真値としてよいか**: judge は Haiku の判定であり誤りうる。L1 の正解ラベルは人手で
  付けているので L1 はこの問題を持たないが、L2 は持つ。**L2 の judge=真値は暫定の割り切り**で、
  対案 F（人間 y/n 確定分）へ移行する道を残す
- **柱3との共通ボトルネック**（cold review [Should]）: L2 と柱3の指摘率は同じ判定スループットに
  律速される（未判定 6,353件・200件/日・1バッチ 180秒タイムアウト）。**L1 を主に据えたのは
  この結合を切るため**だが、L2 を将来 headline にするなら判定スループットの改善が前提になる
- **30件・30%・50% の3閾値**: いずれも暫定。統計的な根拠は「CI 幅が実用域に入る」ことのみで、
  外部基準は無い（§1 の測定不能事項）

### 拡充作業の手続き（再現性・ゲーム防止の記録）

- 抽出は固定窓 [2026-07-27, 2026-08-12) の eligible 母集団 1,118 件から、既ラベル分を除いた
  残余に対する単純無作為抽出（seed は上記 P10）。**machinery-suspect の追加抽出は 0 件**
  （既に全件がラベル済みのため、層構成は拡充前後で変わらない）
- ラベル担当は検出器の実装（`rl_common/detection.py` / 本 harness / `correction_detect.py`）を
  読まない条件で作業した。**どの語にマッチするかを知った状態のラベルは検出器に有利に歪む**
- 一致度検証は、ラベルを伏せた 50 件を**別の2名**が独立に判定（P12）。3者多数決で 6 件を修正し、
  当該レコードに `adjudicated` / `rater_labels` を残した
- **凍結**: 以降、本番の検出パターンを変更する前に評価セットを増やさない。増やす場合は
  seed と実施日を本節に追記し、変更前後の値を両方報告する
