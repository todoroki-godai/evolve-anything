## この分解から言えること／言えないこと

**言えること（観測）**

- **判定器に実際に掛かった correction は 75 件中 3 件**で、その 3 件は違反なしと判定された。
  観測件数は 75 → 8 → 4 → 3 → 0（join → last_skill あり → 解決 → 判定対象 → 違反）。
  除外された入力の判定と入口を広げた場合の産出は測っておらず、**原因の寄与は未測定**
- `plugin:skill` 形式の解決は**本番経路では機能している**（3/3 解決）。前 artifact の
  「解決 0」は計測スクリプト側の旧規則による値であって、本番の状態ではない
- 4件の脱落は `readable-report` の実体が**いずれの場所にも無い**こと（プラグイン／
  `~/.claude/skills`／PJ ローカルの3経路すべてで hits 0）。廃止は claude-config の
  `5f76c75`（main に在り、`skills/readable-report` は main のツリーに存在しない）
- **解決できたのに critical 行が 0 だった 1 件（`status-recap`）は、本番の出力に一切現れない**
  — `runner.py:491-492` は `continue` するだけでカウンタも `unresolved` も増やさない。
  当PJで 8 件中 1 件が**無音で消えている**（silence != evaluated の穴）

**言えないこと**

- **判定器が取りこぼしたかどうかは本分解では判定できない**。3 件が全て None だったことは
  「見逃していない」証明にならない（3 件とも見逃しでも同じ 0 になる）。標本も小さすぎて
  再現率・精度は評価できない
- 「A 案で朝の y/n に何件届くか」は本分解では出ない。観測件数は 75 → 8 → 4 → 3 → 0 で、
  S1（`last_skill` truthy）は当PJで 8/75。入口を広げたときの産出は測っておらず、
  **原因の寄与は未測定**

## 転記忠実性の機械確認

本スクリプトは本番ループを転記して計測点を挟む方式なので、転記が本番と食い違っていないかを
2つの照合で確かめる。

### ① 実測の照合（`matches_production = true`）

| 突き合わせた値 | `run_discover()` | 本分解 |
|---|---|---|
| `instruction_violations` | 0 | 0（S5） |
| `instruction_violations_unresolved` | 4 | 4（S3） |
| `instruction_violations_error` | なし | — |

**①だけでは転記ズレを検出できない**。実測が 0 件なので `0 == 0` は転記が壊れていても通る
（`break` の位置違い・引数の取り違え・スライス方向の逆転は、いずれも S5=0 のまま）。
`unresolved` の一致も、S3 は本番と同じ関数を同じ順で呼んでいるため事実上恒真。

### ② 陽性対照（`both_detect_one = true`）

違反が**在る**入力を注入し、両経路が 1 を返すことを確かめる。実測で S5 まで到達した
スキルの SKILL.md から実際に抽出された critical 行を1本取り、その本文をそのまま message に
した合成 correction 1件だけを `discover.runner._fetch_corrections_with_last_skill` の
戻り値として差し替える（実ストア・実ファイルは書き換えない）。

| | 値 |
|---|---|
| 注入したスキル | `skill-creator:skill-creator`（SKILL.md の 26 行目の critical 行） |
| 本分解の S5 | **1** |
| `run_discover()` の `instruction_violations` | **1** |
| 判定の種類 | `keyword_overlap` |

**陽性対照の限界**: 通ったのは keyword overlap 側の分岐で、対立動詞検出（Stage 1）は先に実行されるが、そこで確定違反を返さず
Stage 2 に進んだ（`scripts/lib/critical_instruction_extractor.py:352` の検査、
同 `:357` の早期 return、同 `:367` の keyword overlap 分岐が根拠）。

## 安全性検証

`write_guard`（`measure_467_proposal_kinds.py` の execution-time monkeypatch を再利用）
と `~/.claude/` マニフェスト差分。LLM 呼び出し 0。
出力ガードは既知の種別（symlink・相対パス）のみ検出する。解決後のパス名で判定するため
hard link は迂回可能であり、保護対象への全書込みを防ぐ保証ではない。

- 段階分解の区間: `write_guard=passed` / `network_guard=passed`（socket・子プロセスとも全ブロック）
- `cross_check` と `positive_control` の2区間: `run_discover()` は本番経路として子プロセスを起動するため、
  **socket だけ塞ぎ、起動した子プロセスの argv を verbatim で記録する**方式に切り替えた
  （名前の列挙で許可・拒否を判定しない）。記録されたのは
  **`git rev-parse --git-common-dir` の2件**（JSON の `cross_check.subprocesses_spawned`）。
  この配列は `cross_check` と `positive_control` の2区間で共有され、件数は両区間の合計。
  `write_guard=passed`
- マニフェスト差分に無関係な PJ の transcript jsonl が `changed` として出ることがあるが、
  execution-time の `write_guard=passed` は、捕捉対象 API と解決後のパス名の範囲で違反を検出しなかったことを示す
  （`guard_no_home_claude_writes` は `builtins.open`/`io.open`/`os.open`/`os.rename` 等を捕捉）。
  **誰が書いたかは本計測では確認していない**（並行する別セッションの追記と**推定**しているだけ）。
  マニフェスト差分は補助的な証跡で、判定は write_guard 側で行う

## 限界

- 実ストアは追記され続けるため、S0・S1 の値は取得時刻で増える（JSON の `measured_at` の断面）
- ここで数えているのは検出経路の産出であって、朝の y/n に実際に出る件数ではない（提示は別経路）
- 当PJのみの母集団。全PJ合算では S1 は 27 件（前 artifact §1.5.1）
