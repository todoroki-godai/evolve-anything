## 段階1（記録）— この rule 自身が2巡で同じ型に当たった

**この rule を作る過程で、同じ軍拡が1階層上で再現した。** 記録しておかないと同じ設計を繰り返す。

- **巡1（第1版）**: 「denylist / allowlist の型を1行で自己宣言する」設計。
  レビュアーの構成した申告文 — `allowlist 型：登録済みストア名を許す形として全列挙し、
  候補パスの resolve/casefold 後の basename が登録名集合に完全一致しない場合は reject する`。
  **名称は allowlist でも、実体同一性ではなく名前の有限列挙に依存するため元の write barrier と同型に破れる**
- **巡2（第2版）**: 「集合の向きではなく識別の閉性を、判定手順1〜5で裁定する」設計。
  レビュアーの構成した申告文 — `①母集団=専用ストアと同じ実体への全書込み ②識別=samefile の device+inode
  ③根拠=hard link を含む全別名は同じ inode へ写る ④陰性試験=既存の別 inode への書込みは reject
  ⑤名前追加不要`。**宣言先が未作成のときだけ `samefile` 失敗を allow する実装でも1〜5をすべて満たす**
  ＝実測表の PR #614 巡2 の fail-open 事故がそのまま再発する。
  別解として `①母集団=store_write(store_id, …) に渡る登録済み ID` と**母集団を狭く申告するだけ**でも
  「閉じている」と裁定でき、direct `open` / `os.write` / `rename` は母集団の外に置かれて塞げない
- **巡2 のその他の [Must]**: 「閉じている＝同じ実体を指す別の表現が存在しない」という定義は、
  hard link・複数 fd という別表現が現に存在する以上、**inode 検査すら文字どおりには不合格**になる。
  発火時点（設計着手前）に「実装を壊す陰性試験の結果」を要求するのは循環している（まだ実装が無い）。
  「とれる手はいずれか」に advisory 単独を並べると、advisory 化するだけで決定論チェックへの翻訳を省略できる
- **裁定（人間・2026-09-03）**: 2巡で族打ち切り。**「健全さの判定手順」を書くことをやめ**、
  ①破れた識別4種を名指しして blocking から外す ②別の人間が裁定する ③壊す入力を実際に構成する、
  の3点に縮小した。**証明の様式を定めるほど、それを満たす申告文が構成される**という実測に従った
