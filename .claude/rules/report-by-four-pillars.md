# 進捗・残タスクは4つの柱で報告する

残タスク・進捗・優先順位は CLAUDE.md「目指すユーザー体験」の柱1〜4 ごとに現状を示す。issue 番号順・作成日順で並べない（柱の名称と定義は CLAUDE.md が単一ソース。ここに写して二重管理しない）。

**固定の並び**: 柱1 → 柱2 → 柱3 → 柱4 → **健全性** → **後回し**。各レーンは `現状（証拠）／ボトルネック／次の一手` の3点で書く
- **健全性レーンは柱に属さない**（正しさ・安全・テスト基盤・技術的借金）。柱に無理やり紐づけて正当化しない。**柱は優先順位の物差しであって取捨ではない**
- **後回しは理由つきで明示する**。黙って一覧から消さない
- 各柱の現状は**実測値**で書く。目標文をなぞらない（#376 を自分の報告にも適用する）
- **数値をこの rule にも CLAUDE.md にも書かない**。フル報告時に `bin/evolve-audit --growth`（柱3）と `bin/evolve-revert --list`（柱4）を実行して取る。同一セッション内は取得時刻を添えて再利用してよい（毎ターン実行しない）
- **測定手段（実測 2026-09-02）**: 柱1〜柱4はいずれも `bin/evolve-audit --growth` で取得する。柱1の評価セットは git 管理外（`.gitignore:25`）だが checkout 同梱と共有 DATA_DIR の両方を探すので worktree からも測れる（**実体を持たないマシンでは測定不能**・#602）。**柱2は「実際に反映された改善（直近30日）」の行が正典**（#587 の専用ストア `reflect_apply_events.jsonl` を read 時に照合する。PR #596/#599 で配線済み）。同じ出力の「**採用した改善（直近30日）**」は**提案の accept という別物なので柱2に流用しない**。申告ベース（`correction_review_seen.jsonl` の `promoted` / `already_reflected`）も照合が無いので使わない。**柱2の行が `measured=False` を示すとき（「測定不能」表示）は数字を書かず、その旨と理由を書く**。柱3は同コマンドによる全 PJ 合算。取得不能なら `not_measured` と書き、推定値で埋めない
- **コマンドの成否を exit code で判定しない**。`bin/evolve-audit --growth` は生成に失敗しても 0 を返す（実測: 例外を握って本文に「生成に失敗しました」の1行を足すだけ）。**出力本文に「失敗しました」が無いこと＋期待セクションが実在すること**で判定し、欠けていたら `測定不能: <理由>` と書く。古い値で補完しない。他レーンの報告は続ける
- ボトルネックは各柱1件。柱をまたぐものは「共通ボトルネック」を最大1件だけ置き、各柱からそれを参照する（同じものを4回書かない）

**未実測**: この rule を置くことで報告の挙動が実際に変わるかは測っていない。指示文書のロードと遵守は別（#494 と同じ問題）。
