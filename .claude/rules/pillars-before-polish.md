# 4本の柱を先に端まで通してから磨く
**発火条件**: 独立して完了判定できる成果物について着手順・優先度・着手可否を提示するとき。**候補が1件でも、着手前にその1件を分類することを提示に含める**（提示せず直接着手する経路を塞ぐ）。分類には意味判定が残るため、各候補へ下記4分類のどれかと根拠を併記して先後を可視化する
- **先後の全順序**: 健全性（正しさ・安全・データ破壊防止）＞立証済みの配線断（`observation-first.md`）＞柱1〜4の完通＞磨き込み（柱のどれかが未完通なら磨き込みへ着手不可）。これは `report-by-four-pillars.md` の表示順とは別の着手順である
- **候補どうしの先後は、依存の実在を確かめてから置く**（上の全順序は候補「群」の間の順序で、本項目は同じ群の中の個別候補の話）。「A の後でないと B に着手できない」と書くときは、**A が初めて生む成果物を1つ名指しする**（＝A の完了前には存在も確定もせず、かつ B の着手に必要な内容。**「B が A の触るファイルを読む」では足りない** — 旧版で着手できる／A の結果を後から取り込めるなら依存ではない）。名指しできないなら**並行に着手できるものとして扱う**。**共有可変資源の競合（同一ファイル・同一ストアへの書込み）は依存として数えてよいが、その場合の処置は順序づけではなく `worktree-parallel.md` の隔離・割当てが正典**。出所: 2026-08-26 ユーザー指摘（`correction_id: 6aa19261`）「並行して、今すぐ作って。561の後じゃなきゃダメってことあるの？」— 実際に依存は無く、順序制約は自分で置いた思い込みだった
- **境界裁定（列挙は閉じている）**: 健全性は現在の誤動作・安全違反・データ破壊、またはその判定に必須なテスト基盤の故障だけとし、行数超過・stale参照・技術的借金・重複・命名・可読性・整理は磨き込みへ倒す。**例外は、それが現在の誤動作・データ破壊を現に引き起こしている実証（`observation-first.md` と同型の立証5点）を添えた場合だけ**で、実証が無い限り繰り上げない
- **柱の判定**: 目標値は別途定める（暫定）ものとし、値と根拠は issue #567 が正典。到達は現時点では人間が証拠を読み判定し、機械判定は切り出し先 issue の担当である。**証拠が取得不能な柱は未通と同じ側（磨き込み着手不可）へ倒し、測定不能である旨と理由を併記する**（測定不能を到達扱いにしない）
- **スコープ（実測 2026-09-02）**: 柱1の評価セット `scripts/bench/a0_eval_set.jsonl` は **git 管理外**（`.gitignore:25`・他PJの生発話を含むため commit しない）。checkout 同梱と共有 DATA_DIR の `bench/` の両方を探すので worktree からも測れるが、**実体を持たないマシン・fresh clone では測定不能**（PJ非依存だがマシン依存・#602）。柱2・柱4は当PJ（slug）、柱3は全PJ合算であり、「4本の完成度」と並べても別のものを測る
- **既存ゲート**: 柱の完通を急ぐことを理由に `review-round-cap.md` と `design-review-gate.md` の必須レビュー巡・[Must]解消を省略または上書きしない
